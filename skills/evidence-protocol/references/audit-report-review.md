# 审计报告复核方法论

> 来源：2026-08-24 复核《PA存储运算效率与架构审计_20260824.md》——文档大方向正确但 8 处事实偏差 + 2 处铁律冲突 + 3 项已完成项被当待办，照单执行会浪费约 3h。
> 核心：**审计报告是「他人的断言」，复核=用第一手实测证据逐条判定，不凭印象接受或否定**。

## 触发场景
- 用户给出审计/分析/优化报告，说"复核/验证/提升/数据对不对"
- 外部 AI 报告 / 文档建议需要落地前筛查
- 自己或他人产出的整改清单需要重排优先级

## 五步流程

### ① 静态实测验证（不信任自报数字）
对报告的**每一个量化断言**做第一手验证，三态判定：

| 判定 | 含义 | 处理 |
|------|------|------|
| ✅ 属实 | 实测与断言一致 | 保留 |
| ⚠️ 偏差 | 方向对但数字/归因有差 | 修正数字+归因 |
| ❌ 不成立 | 断言与事实相反 | 删除该条+其整改建议 |

**验证工具库**（Windows Git Bash + 托管 python）：
```bash
# 文件统计（数量/大小/分布）
find . -maxdepth 1 -name "*.pkl" | wc -l
du -cb ./*.pkl | tail -1                    # 总大小
ls -laS ./*.pkl | head -11                   # 最大 top
find . \( -name "*.db" -o -name "*.sqlite*" \) -printf "%s %p\n" | sort -rn

# 代码静态计数（grep 计数，注意口径）
grep -c "\.copy()" core/signal_engine_v1.py
grep -rl "import X" --include="*.py" . | grep -v __pycache__ | wc -l   # import 中心度

# SQLite 实查（只读模式！绝不开写）
python -c "
import sqlite3
c = sqlite3.connect('file:xx.db?mode=ro', uri=True)
cur = c.cursor()
cur.execute('PRAGMA index_list(表)')      # 索引存在性
cur.execute('PRAGMA journal_mode')        # WAL?
cur.execute('PRAGMA freelist_count')      # 膨胀? VACUUM 必要性
cur.execute('SELECT COUNT(*) FROM 表')    # 行数
"

# 源码定位（验证「已优化/已修复」类断言是否过时）
grep -n "关键代码模式" 模块.py | head     # 看注释/版本标记判断新旧
```

**验证清单要点**：
1. **计数口径陷阱**：如"232 处 iloc 归 signal_engine"实测是 core/ 全目录合计（signal_engine 仅 116）——分清"单文件 vs 目录合计"
2. **"已修复"断言必查**：报告列的 bug/瓶颈可能已修复（查代码注释里的修复日期），修复后仍排工=浪费
3. **数据库健康断言必实查**：无索引/无WAL/需VACUUM 这类假设常不成立（实测 signal_history.db 已有 2 索引+已 WAL+freelist=0，3 条整改建议全落空）
4. **生产模块重复实现比实验脚本更严重**：grep `^def ema` 等重实现时，execution/core 生产目录里的命中优先于 experiments/

### ② 铁律冲突审查（对照项目铁律，报告常缺失）
整改建议逐条对照铁律库，冲突项必须加约束或改方案：
| 铁律 | 冲突示例 | 处理 |
|------|---------|------|
| 凭据安全（key 不写文件） | 建议"LLM 配置迁入 llm.json" | 加硬约束：api_key 只走系统环境变量，文件只放非敏感项 |
| 结论扩散（变更三处同步） | 计算优化/内核改动 | 改完必跑全史回归，E_R/PF/n 逐位一致才算通过 |
| 隔离优先（可开关可回退） | 大重构/引擎拆分 | 生产运行期留旧路径开关，禁止一把梭 |
| 时间窗口（省 token） | 报告排「本周/短期」节奏 | 执行以用户指定窗口为准，报告排期仅参考 |

### ③ 已落地项标注（防重复排工）
报告建议里可能已部分/全部完成——实测确认后标注 ✅ 已完成，从待办清单剔除：
- 查代码注释修复日期 / 配置文件现状（如 api_key_source=system_env 即凭据安全已落地）
- 查 git log / 日志里的修复记录

### ④ 按当前生产状态重排优先级
原报告按 ROI 排序，复核后按**生产风险**重排：
- **P0 立即做**：零风险（删旧备份/只读维护/加缓存不改逻辑）——可直接执行
- **P1 短期做**：需回归验证（计算优化/内核改动）——改完必跑对比
- **P2 有条件做**：试点/隔离验证（格式迁移/并行化）——先试点再推广
- **P3 暂缓**：生产运行期高风险的（大拆分/重写）——等窗口或拍板

### ⑤ 输出模板
```
# XX审计 · 复核提升报告
一、复核总评（原评分 vs 复核后 + 一句话结论）
二、逐项复核结果（✅/⚠️/❌ 三态表，含实测数字）
三、铁律冲突审查（建议 vs 铁律 vs 裁定）
四、已落地项（原报告未标注）
五、复核后优先级总表（P0-P3）
六、复核总结（如果只做 3 件事）
```

## 边界与纪律
1. **只读验证**：复核过程 sqlite 必须 mode=ro，不做任何写操作；删文件/改代码属于清扫阶段，需另行确认
2. **不下未经实测的结论**：验证不了的条目标注「待核」，不猜测
3. **复核≠执行**：复核产出修订版方案，执行（尤其改动生产）需用户拍板或按待办分类规则
4. **实测数字写进报告**：复核报告必须带"报告断言 vs 实测值"对照，让用户能 5 秒内证伪
